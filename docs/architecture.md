# Compiler architecture

This document walks through how `pud` turns Puddi source into a WebAssembly component. It is meant for people working on the toolchain; users should start with the [documentation](https://puddi-lang.github.io/puddi-docs/).

## Overview

```text
 .pud sources ──► lexer ──► parser ──► derive ──► program ──► elab ──► opt ──► codegen ──► core module
 (user, std,                  (AST)    (@derive    (items,    (types,   (WAT, then   │
  prelude,                              as source)  names,     IR)       binary)     ▼
  platform,                                         signatures)                 wit-component
  WIT bindings)                                                                 ──► component
```

Every stage is in `src/`. The driver (`driver.rs`) runs them in order and collects diagnostics; `main.rs` implements the `pud` commands on top of it.

## Sources

A compilation is more than the user's files. The driver assembles:

| Source | File | Notes |
|---|---|---|
| User modules | `src/**/*.pud` of the package and its dependencies | loaded by `main.rs` and `deps.rs` |
| Prelude | `src/prelude.pud` | types, traits and functions available everywhere |
| Numeric prelude | generated by `numeric.rs` | methods and trait impls for every integer and float type |
| Standard modules | `std/*.pud` | compiled in only when imported |
| Soft float | `src/soft.pud` | float formatting and parsing for targets without a JavaScript host |
| Platform layer | `src/platform_*.pud` | host access for `wasi` and `plugin` components, replacing the JavaScript host imports |
| WIT bindings | generated by `wit.rs` | Puddi source for every imported WIT interface |

The prelude, standard modules and platform layer are embedded in the binary with `include_str!`. Most of the runtime is therefore written in Puddi and goes through the same pipeline as user code. Low-level operations are reached through compiler intrinsics with a `__` prefix (`__host`, `__cast`, `__global` and others), which user code should not call.

## Stages

**Lexing and parsing** (`lexer.rs`, `parser.rs`, `ast.rs`). A hand-written tokenizer and recursive-descent parser produce the AST. Newline handling (SPEC 2.5) happens in the lexer: it decides whether a newline ends a statement from the surrounding tokens. `driver.rs` cuts large files at lines holding only `}` and lexes and parses the pieces on separate threads, falling back to one piece when a cut does not lie between two items. `main.rs` keeps the output of each component build in the user cache directory, keyed by every input, and reuses it when nothing changed.

**Derive** (`derive.rs`). `@derive(...)` is expanded into ordinary `impl` blocks, generated as Puddi source and parsed like the rest.

**Program** (`program.rs`). Collects items from all modules, resolves imports and names, and resolves the signatures of functions, structs, enums, traits and impls. It enforces visibility, coherence and target filtering (`@target`).

**Elaboration** (`elab.rs`, `types.rs`, `exhaust.rs`, `ir.rs`). Type inference and checking of function bodies, and lowering to a typed IR in which every type is concrete. Generic functions are checked per instantiation and monomorphized: `elab.rs` keeps a queue of function instances, seeded with the entry points and exports, and elaborates each instance once. Implicit widening, `?` with `From`, `dyn Trait` coercions, closures and their captured variables, and async functions are all lowered here. `exhaust.rs` checks `match` exhaustiveness with the usefulness algorithm.

**Optimization** (`opt.rs`). Rewrites each function's IR before code generation. It inlines higher-order and tiny calls, calls that match on a constructor argument, and one level of small recursive calls. It also forwards immutable struct fields and selects `match` arms for known constructors. The [liveness tape](tape.md) removes unused values and retains required checks, including the bounds checks of discarded scalar array reads. `PUD_NO_OPT=1` skips optimization.

**Code generation** (`codegen.rs`). Turns IR into WebAssembly text using WasmGC types, one function at a time on several threads (each with its own copy of the state, merged in function order): structs and enum variants become GC structs (enum variants are subtypes of a base struct), closures and trait objects are GC structs with function references, and integer overflow checks are inlined. `ranges.rs` tracks the value ranges of integer locals implied by `if` and `while` conditions, and codegen leaves out the overflow checks those ranges rule out. `asm.rs` assembles the text into a binary core module, encoding function bodies on several threads; it understands the subset of the text format codegen writes and falls back to the `wat` crate for anything else (`PUD_ASM_CHECK=1` checks that both give the same module).

**Components** (`wit.rs`). Loads WIT worlds with `wit-parser`, generates the bindings for imported interfaces (including canonical ABI lifting and lowering, written as Puddi), generates export wrappers that check the user's `export fn` items against the world, and encodes the final component with `wit-component`. The bundled WASI 0.3 and `puddi:runtime` WIT files are in `wit/`.

## Targets and hosts

| Target | Host side |
|---|---|
| `wasi` | `runner.rs` runs the component in the embedded Wasmtime with WASI 0.3 (copying collector; compiled components and Cranelift's per-function output cached in the user cache directory), and implements the `puddi:runtime` worker interfaces by instantiating the component again on another OS thread |
| `browser` | `runtime.mjs` (embedded and written out as `puddi.mjs`) extracts the core module from the component and instantiates it with JavaScript host functions; it also runs `pud test` and `PUD_HOST=node` under Node.js |
| `plugin` | the application that loads the component; `pud run --target plugin` uses `runner.rs` to call one export |

The embedded runtime is the `runtime` cargo feature (on by default). `cargo build --no-default-features` leaves out Wasmtime, which makes the build much faster.

## Other tools

- `deps.rs`: git and path dependencies, minimal version selection and `pud.lock`.
- `tools.rs`: `pud fmt` and `pud doc`.
- `diag.rs`: source maps, spans and diagnostic rendering.

## Tests

`tests/run.rs` runs the regression programs in `tests/run` and `tests/fail` and the plugin example; `tests/conformance.rs` runs the [conformance suite](../conformance/README.md) against the binary cargo just built. See [CONTRIBUTING.md](../CONTRIBUTING.md#testing).
